What is this?

This system takes a business requirement, investigates a real Spring Boot codebase using retrieval-augmented search, proposes a specific code change, and applies it only after a human explicitly approves — a boundary enforced outside the model's own tool access, not merely by prompt or policy. Once approved, the change is compiled and tested with real, controlled tools before ever being reported as verified.

Why the approval boundary matters

Capability does not imply authority. This agent can read, reason about, and propose changes to real code — but approve/reject are plain functions that are never registered as callable tools and never reachable through the dispatch layer, verified by exact-match tests, not string matching. If no human is present, the system fails closed (rejects) rather than silently proceeding. That distinction — proven with tests, not just described — is the core engineering claim of this project.

What's public today, and why

Public: the Dashboard (architecture, capability, and verification evidence), Sessions (how human + AI time was actually used, honestly scored), and the real Customer application the agent operates on.

Not public: the interactive Control Plane (submit a requirement, click Approve/Reject, watch a live build/test run). It runs locally only — anonymous visitors do not have production release authority, and a safe public write boundary doesn't exist yet. The Dashboard/Sessions pages here are a real snapshot published from that local system, not a live connection to it.
