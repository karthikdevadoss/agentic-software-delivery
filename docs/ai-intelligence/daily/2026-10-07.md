## 2. Model/tool recommendations today

- If a coding AI assistant blocks routine technical work (like debugging a crash log) with a vague "security" warning, don't assume it's a one-off glitch specific to that tool — the same false-alarm pattern has now shown up independently in two different vendors' products, suggesting it's a shared weakness in how these safety filters currently work, not one company's bug.
- If you use an AI agent feature that can auto-escalate to more expensive, higher-effort processing, check your actual usage directly rather than trusting that it roughly matches how much you asked it to do — it can run far more than expected with no clear accounting afterward.
- If you use any multi-AI-agent setup where one process reports task results back to another, and you ever restart the "lead" process, double check that reports are actually arriving afterward rather than trusting a "sent successfully" message — a real bug showed this signal can be wrong right after a restart.
- Treat any brand-new AI model's own performance claims with real skepticism until an independent group verifies them, regardless of how confident the announcement sounds.

## 8. One experiment worth running

Building on yesterday's idea (testing whether an automated check can fail silently and still report "all clear"), today's finding suggests a second, related test: if you use any setup where one process or script reports back to another (even something simple, like a background job emailing a status update, not necessarily a full multi-AI-agent system), deliberately restart or interrupt the main/coordinating part of that setup mid-task. Then check whether a "done" or "sent successfully" signal from the other part still means what it says afterward, or whether it can report success while quietly doing nothing. This turns one bug report into your own concrete answer about whether something you already trust to tell you "it worked" could be lying to you specifically around a restart.
