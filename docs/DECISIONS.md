# Architecture Decisions

- Original Ticket-to-Implementation-Plan Agent is V1 of a larger Agentic Software Delivery System.
- Real Spring Boot Customer application is used as the target system.
- Update Email intentionally remains unimplemented so we have a visible before/after agent ticket.
- V2 uses bounded direct repository context.
- V2 is NOT RAG.
- RAG should be introduced when selective retrieval becomes justified.
- Browser UI exists so agent-driven changes can be visibly verified.
- Human approval remains required before production deployment.
- V3 uses direct client-side Anthropic tool calling (list_repository_files, read_file, search_code) rather than an MCP server. MCP remains deferred until multiple tools/agents actually need to share a common protocol — introducing it earlier would be speculative infrastructure with no current consumer.
- V3's read-only tool set has no write capability by design. Any file-modifying capability is a distinct, higher-risk decision (V4) requiring its own explicit review of write boundaries and approval gates — it does not follow automatically from V3 being verified.
- Introduced docs/LESSONS.md as a separate small file for durable, reusable technical gotchas (e.g. API/tooling edge cases), distinct from DECISIONS.md (why we chose an approach) and PROJECT_STATE.json (current status). Why: by V3 enough concrete, reusable lessons had accumulated (thinking-block handling, tool_result batching, stop_reason pitfalls) that leaving them buried in code comments risked future sessions rediscovering the same failures.
- Enriched verification_state in PROJECT_STATE.json from plain booleans to {status, as_of_commit, evidence} objects instead of creating a separate verification-tracking file. Why: this gives future sessions enough to judge whether a "verified" claim might be stale (by comparing as_of_commit against later changes to the same files) without duplicating the same facts across two files.
- Product north star refined and confirmed this session — see the "Final Goal" section of PROJECT_STATUS.md (updated to match) rather than restating it here; this file only needs to record that human involvement is explicitly scoped to product/business/ambiguity/risk/security/production decisions, with routine investigation/implementation/testing/diagnosis/retry/verification/doc-updates moving to agents over time. Does not replace the V1->V4 execution roadmap — it's the "why" the roadmap exists.
- **[SUPERSEDED, see next entry]** MCP adapter (Phase A) was initially built on standalone **fastmcp** (PrefectHQ). Kept here (not deleted) so the reasoning trail is visible: chosen for its dominance/ergonomics after verifying the official SDK had renamed its bundled class to `MCPServer` and dropped `mcp.server.fastmcp`.
- MCP adapter **migrated to the official `modelcontextprotocol/python-sdk`** (`mcp` package, `MCPServer` class) while the surface was still tiny (4 thin wrapper tools, 2 files). Why: re-verified against current official docs and empirically tested that the official SDK — the actual Tier-1/spec-owner implementation — provides everything fastmcp offered for our needs: `@mcp.tool()` decorator registration, `mcp.run()` for stdio (default) and `mcp.run(transport="streamable-http", ...)` for hosted deployment, and (confirmed by direct empirical test, not just docs) an in-process `Client(mcp_server_instance)` for testing, identical in capability to fastmcp's `Client`. Being the spec-owner reduces the exact naming-churn risk we already got bitten by once (see LESSONS.md). `mcp_server.py` still contains zero tool logic of its own — every tool calls straight into `tools.py`; `tools.RepoToolError` is now re-raised as the SDK's `ToolError` so the *specific* failure reason reaches the client (verified: a traversal rejection surfaces its exact message, not a generic "tool failed"). Verified: official SDK docs/spec confirm SSE transport is still retained for backward compatibility (not removed) — Streamable HTTP is the *recommended* choice for new hosted work, not the *only* supported one.
- Transport choice: stdio for local dev/demo now (matches how local MCP clients like Claude Desktop/Claude Code normally connect; simplest, no auth surface). Streamable HTTP (`transport="streamable-http"` in the official SDK) is the documented path for a future hosted multi-tenant platform — verified that the current MCP spec (2026-07-28) made this transport stateless (no more `Mcp-Session-Id`/sticky sessions), so it can run behind an ordinary load balancer without per-server affinity when we actually host it. Not yet run/tested (only stdio has been exercised) — tracked as ACTION_QUEUE ACT-005.
- RAG (Phase B) embeddings: default provider is **fastembed** (`BAAI/bge-small-en-v1.5`, ONNX runtime, no PyTorch, no API key) — chosen for a working, verifiable local demo today with zero credential blockers, confirmed to actually run on this Windows machine (see LESSONS.md for one first-run Windows caching quirk). Anthropic has no embeddings model of its own; **Voyage AI's `voyage-code-4`** (released 2026-08, supersedes `voyage-code-3`) is currently their recommended code-embedding model — re-verified this session rather than reusing the earlier `voyage-code-3` reference (see Standards Freshness below). A `_embed_voyage()` provider is implemented in `agent/embeddings.py` (model `voyage-code-4`, 1024-dim Matryoshka output) and selectable via `RAG_EMBEDDING_PROVIDER=voyage`, but is not usable yet — it requires `VOYAGE_API_KEY`, which is not configured. No key was fabricated or hardcoded; switching providers later is a one-line env var change, not a rewrite.
- RAG index storage: a single local JSON file (`agent/.rag_index/index.json`, gitignored as derived/build data) plus an in-memory numpy cosine-similarity scan — not an external vector database. For this repository's current size (dozens of files, ~40 chunks), a linear scan is genuinely fast and simple, not a compromise; swappable later behind the same `semantic_search()` call if the repo grows enough to justify Qdrant/pgvector. Chunking is a simple fixed 40-line sliding window (8-line overlap), not AST-aware — a deliberate speed tradeoff; revisit only if retrieval precision proves insufficient in practice.
- RAG index is **incremental**, not rebuild-from-scratch (resolves ACTION_QUEUE ACT-004): each file's post-redaction text is content-hashed; unchanged files reuse stored chunk vectors with zero re-embedding calls; changed/new files are re-chunked and re-embedded; removed files drop out of the index. A full rebuild only happens when there's no existing index or the embedding model/chunking strategy is incompatible with what's stored. Index schema keys chunks by a stable id (`path#start-end`) in a dict, not by array position — chosen specifically so partial add/update/remove is a simple dict operation, not fragile index-juggling (see LESSONS.md). Verified live: second build with no changes embedded 0 chunks (44s -> 72ms); a fixture add/modify/delete each triggered exactly the expected single-file re-embed or removal.
- Hybrid retrieval is enforced, not just described: `semantic_repository_search`'s tool description and the V3 system prompt both state results are candidates only, and this was verified empirically — a live run treated an unread semantic-search hit (`index.html`) as unverified rather than asserting facts about it, exactly matching the intended "RAG finds the haystack, tools verify the needle" philosophy.
- `agent_loop.py`'s core tool loop required zero changes to support the new `semantic_repository_search` tool — it already dispatched generically over whatever `tools.TOOL_SCHEMAS` contains. This validates the earlier V3 architectural choice not to hardcode tool names in the loop itself.
- Added `agent/metrics.py`: a tiny in-memory structured-event interface (`record_tool_call`, `record_rag_index`, `record_retrieval` + matching getters) wired into `agent_loop.py`, `mcp_server.py`, and `rag_index.py`. Why: the future AI Engineering Intelligence dashboard needs clean per-call/per-build metrics (tool name, duration, result size, blocked-unsafe flag; RAG scan/reuse/embed counts; retrieval latency/candidate counts) — this is the smallest interface that lets that layer consume real data later without these modules being rewritten, without building a database or dashboard now, and without logging secrets/raw content/thinking.

- Added `docs/CONSTITUTION.md` (Layer-0 operating principles, Gita-inspired but explicitly not a scriptural claim) and `docs/ROADMAP.md` (long-term vision: two dashboard audiences, session/AI-engineering intelligence, metric north stars, multi-agent roadmap, enterprise benchmark ladder — all future increments). - V4 write boundary (`agent/write_tools.py`): a strict propose → approve → apply flow, not direct file access. `propose_edit(path, new_content)` takes the *full* new file content (not a line-based patch) — simplest correct approach for a first foundation, handles both "modify existing file" and "create new file" uniformly, and the agent already has `read_file` to construct the new full content from the current one. Reuses `tools._resolve_safe_path` directly (traversal/absolute/symlink/secret-name checks) rather than reimplementing them, adding only a write-specific restriction on top.
- Write scope is deliberately narrow: only `app/src/main/java/` and `app/src/test/java/`, `.java` files only — not `pom.xml`, not `docs/`, not `agent/` itself. Why: this is exactly what implementing the Update Email ticket will need (controller/service/repository/entity/test changes), and expanding write scope is a scope decision that should be made explicitly later, not implied by "it would be convenient."
- Compile/test tool (`agent/build_tools.py`) is allowlist-only (`compile`, `test`), never a general shell tool — `subprocess.run()` is always called with an explicit argv list (`shell=False`), so no input could ever reach a shell interpreter. Verified live: both goals actually ran against the real Customer app (`mvnw compile` succeeded in ~15s, `mvnw test` succeeded in ~11s with zero test classes present, as expected since no tests exist yet).
- Found and fixed a real security gap in `tools._resolve_safe_path` while building the write boundary: the secret-filename block only ran `if resolved.is_file()`, silently allowing a **new** file named e.g. `credentials.java` to be proposed. Fixed by removing that guard (see LESSONS.md); re-verified all 24 pre-existing tests still pass. This fix benefits the read-only tools and MCP adapter too, not just V4 — found via V4 testing, but the fix is in the shared boundary all paths rely on.
- V4's write/build tools are **not yet wired into the live Claude tool-calling loop** (`agent_loop.py`'s `TOOL_SCHEMAS`/`dispatch_tool_call`). Why: this task's explicit scope was the safety mechanism itself, verified in isolation via direct calls and automated tests — deferring the live-wiring step (and the first real use against the Update Email ticket) keeps this checkpoint reviewable on its own, per the constitution's "smallest useful step" principle, rather than bundling mechanism + first real usage into one unreviewed change.
- Approval is bound to a `sha256(path, content)` hash captured at `approve_edit()` time and re-verified at `apply_edit()` time, not just an `approved` boolean. Why: found via deliberate testing that a boolean alone doesn't prevent the approved content/target from being substituted before apply (see LESSONS.md); a hash binding is the smallest deterministic mechanism that closes this without crypto libraries, a database, or an auth server — appropriate for this local, single-process MVP. `approve_edit`/`reject_edit` themselves remain plain Python functions never registered in `TOOL_SCHEMAS` — the trust boundary is "not reachable from LLM tool dispatch," not a permissions system.
- Public deployment split into two separate targets, not one. (1) `public-site/` — a static Vercel deployment (new project `agentic-software-delivery`, distinct from the existing `portfolio` project) serving Dashboard/Sessions as a committed JSON snapshot, reusing `agent/web/{dashboard,sessions}.{html,js,css}` unmodified via `vercel.json` rewrites (`/api/dashboard` → `dashboard.json`, same for sessions) — chosen because Vercel serverless functions can't host our Starlette app's background threads/SSE/in-memory `RUNS` state, and a static snapshot is the smallest honest thing that's genuinely publicly reachable today. The interactive Control Plane (submit/approve/reject) is deliberately NOT deployed publicly — no safe public write boundary exists yet, and anonymous visitors must not gain production authority (see CONSTITUTION.md capability-does-not-equal-authority). (2) The actual Spring Boot Customer app needs a JVM-capable host — Vercel cannot run Java at all, so it's out of scope for that target regardless of app maturity; Railway was chosen as the smallest fit (free tier, auto-detects Maven/Java via Nixpacks, no Docker required locally) but requires the creator's own one-time browser authorization (`railway login`) before anything can be deployed there — not something this agent can complete unattended.
- "Public data changes without redeploy" is explicitly NOT implemented yet — today's snapshot requires regenerating the two JSON files and redeploying. A live version needs a small KV/Blob store (Vercel Blob or similar) so a local "publish" step can update public data without a full redeploy; deliberately deferred to keep today's deployment inside the timebox rather than adding new cloud infrastructure under time pressure.
- Verified Claude Code's actual supported hook events (SessionStart, SessionEnd, UserPromptSubmit, PreToolUse, PostToolUse, PostToolUseFailure, PermissionRequest, PermissionDenied, Notification, Stop, SubagentStart, SubagentStop) and their stdin JSON field names (hook_event_name, session_id, cwd, tool_name, tool_input, tool_response, prompt, transcript_path, permission_mode, stop_hook_active) by extracting literal strings directly from the installed `claude.exe` v2.1.263 binary's own source (`grep -ao` for the exact identifiers, cross-checked against literal property-access patterns like `e.hook_event_name`), not by trusting a subagent's documentation synthesis. Why: an earlier subagent's answer to this exact question listed several plausible-sounding but unverifiable hook names (e.g. TeammateIdle, WorktreeCreate, PostToolBatch) cited to a GitHub issue rather than a spec page — insufficiently authoritative to build on for a "do NOT invent unsupported hooks" requirement. Binary string extraction is real, first-party ground truth: if a string isn't present in the binary you're actually running, that binary cannot possibly act on it.
- Claude Code development-telemetry hooks (`agent/claude_code_hook.py`) never make a network call in their synchronous path — they call `event_ledger.spool_only()` (build envelope + redact + append to the local spool, zero DB I/O) and then `trigger_background_sync()` (a detached, lock-guarded subprocess that drains the spool via the existing `sync_spool()`). Why: a hook that attempted a live TCP-proxied Postgres connection synchronously would add unpredictable (sometimes multi-second, per this session's own earlier connection-timeout experience) latency to every tool call in every future Claude Code session in this repository — an unacceptable cost for telemetry. Reuses the exact same envelope/spool/idempotent-insert machinery the Workbench event ledger already has; this is one telemetry architecture with two producers (`record_event()` for Workbench, `spool_only()` for Claude Code hooks), not two systems.
- Claude Code development activity is tagged `source="claude_code"`, `activity_class="PRODUCT_DEVELOPMENT"` in the same `delivery_events` table as Workbench runtime activity (`activity_class="PRODUCT_RUNTIME"`), rather than a second table. Why: one append-only ledger with a cheap, indexed discriminator column serves both query needs (`WHERE activity_class = ...`) without the schema-proliferation CLAUDE.md's original P0 task explicitly warned against ("do NOT prematurely create dozens of normalized tables").
- The Windows human-attention notifier (`agent/claude_notify.ps1`) uses only built-in Windows APIs (WinRT toast via the pre-registered legacy-PowerShell AUMID `{1AC14E77-02E7-4E5D-B744-2EB1AE5198B7}\WindowsPowerShell\v1.0\powershell.exe`, `System.Media.SystemSounds`, and `user32.dll`'s `FlashWindowEx` via inline C#) rather than installing a module like BurntToast. Why: Claude Code's own binary was confirmed (via the same string-extraction method) to only support `terminal_bell`/`iterm2`/`auto` notification channels — no native Windows toast channel exists — and a zero-install approach has no new dependency to keep working across machines. Verified live via a real, human-confirmed test: the toast popup was confirmed by the creator; sound and taskbar flash were not affirmatively confirmed in that same test (Focus Assist can mute toast sound, and `FlashWindowEx` is a documented no-op against a window already in the foreground, which was the case during that specific test) — reported honestly as NOT CONFIRMED rather than assumed working.
- Claude Code hook wiring (`.claude/settings.local.json`) is intentionally never committed to Git, even though the referenced script (`agent/claude_code_hook.py`) is portable and checked in. Why: this repository is now public — a stranger cloning it must not have hooks silently start executing scripts or attempting database connections just by opening the folder in Claude Code; enabling this must be an explicit, informed choice made by whoever owns that specific machine (see docs/RECOVERY.md's "Recovering Claude Code development-telemetry hooks" section for the portable, non-secret setup instructions instead).
- Switched the temporary public trainer-preview bridge from Cloudflare Quick Tunnel to `ngrok`. Why: 3 consecutive fresh Cloudflare Quick Tunnel attempts each reported successful tunnel registration with Cloudflare's own edge, yet the assigned `*.trycloudflare.com` hostname never resolved in public DNS even after 10+ minutes per attempt, confirmed via a direct query to Cloudflare's own authoritative resolver (1.1.1.1 DoH) returning NXDOMAIN with a cached negative TTL every time — a real, reproducible symptom, not a one-off flake, and not something retrying the same free/account-less mechanism was likely to fix. `ngrok` required an explicit account/authtoken (the creator completed that step themselves; the token was never seen, printed, logged, or committed) and, separately, an agent binary update (the winget-installed 3.3.1 was below the account's minimum supported version 3.20.0 — resolved via `ngrok update` to 3.39.11) before it would authenticate at all. - Moved the entire Agentic Software Delivery platform backend (`agent/web_server.py` — Workbench/Dashboard/Usage/Learn/Profile) off the creator's laptop onto persistent Railway hosting (a Docker image built from a new repo-root `Dockerfile`), superseding both the Cloudflare Quick Tunnel and `ngrok` detours. Why: a tunnel-fronted localhost server is fundamentally unsuitable as a recruiter-facing URL — it shows a provider interstitial warning page, and goes dark the instant the creator's laptop or tunnel process stops; neither is acceptable for something meant to be shared and revisited independently. Chose "entire platform on Railway" over "Vercel frontend + Railway backend" based on actual, inspected runtime requirements, not assumption: `web_server.py` is a long-running Starlette process with in-memory `RUNS` state, SSE streams, and background threads (already established as incompatible with Vercel serverless functions for the exact same reason the public Dashboard/Sessions snapshot had to be a separate static deployment — see the "Public deployment split into two separate targets" entry above), and the Workbench's real execution path shells out to `git`, `app/mvnw` (needs a JDK), and the `railway` CLI — none of which a serverless function environment supports. Splitting frontend/backend would also have required re-architecting how pages are served (a new build step, CORS) for no benefit, which was explicitly out of scope ("do not redesign Dashboard/Usage/Learn/Profile"). One Docker image, one Railway service, reusing the exact same provider already trusted for the Customer app and the event ledger, was the smallest correct fit for the actual requirements.
- The new backend service (`agentic-platform-backend`) lives inside the *existing* `agentic-delivery-events` Railway project rather than a new project. Why: `railway init` for a genuinely new project failed with a real, verified error — "Free plan resource provision limit exceeded" — while `railway add --service` to add a new service to an already-provisioned project was not blocked. Given the explicit instruction to avoid new paid-tier commitments/business decisions without asking first, adding a service to existing approved infrastructure (not a new billing decision) was judged the correct, minimal-friction choice over stopping to ask the creator to upgrade a paid plan just for project-count headroom. The project-name/service-content mismatch this creates (a "platform backend" living in the "events" project) is recorded here explicitly so a future session doesn't mistake it for an accident.
- Copying `ANTHROPIC_API_KEY` and `EVENT_LEDGER_DATABASE_URL` from the local `agent/.env` into the new Railway service's variables was done via a script that piped each value directly from the local file into `railway variable set KEY --stdin`, reading the value from disk and writing it to the subprocess's stdin without ever assigning it to a variable that gets printed, logged, or returned in any tool output — the same discipline already established for every other secret-handling step this session (see the event-ledger `EVENT_LEDGER_DATABASE_URL` creation, and the `ngrok` authtoken entry above).

Why: generating a project-scoped Railway token requires the Railway dashboard UI — confirmed no CLI subcommand exists for it in the installed CLI (`railway --help`'s full command list has no `tokens`/`token` command) — making this a genuine "stop and tell the creator exactly what to click" point, not something to route around. The acceptance test performed instead deliberately used an already-satisfied requirement (reaches `NO_CHANGE_NEEDED` via read-only investigation only), which doesn't reach the deploy step at all, so the rest of the pipeline could still be proven working end-to-end without this token. A genuine code-change requirement submitted today would currently fail once it reached the deploy step.
- Claude Code development-telemetry hooks moved from `.claude/settings.local.json` to the USER-LEVEL `~/.claude/settings.json`. Why: root-caused (not guessed) via a direct, reproducible test — added a `hooks` key plus a marker key to `.claude/settings.local.json`, ran one ordinary novel Bash command, and watched Claude Code's own permission-remember mechanism (which appends a new rule to `permissions.allow` on every tool-action grant) rewrite the entire file and silently drop both keys; reproduced a second time to rule out coincidence. The identical test against `~/.claude/settings.json` in parallel showed zero mutation across the same triggers — that file is simply not touched by the permission-remember rewrite path. `.claude/settings.local.json` remains exactly right for permission `allow` rules (that churn is its intended job); it is categorically wrong for anything that needs to persist untouched, including hooks. A secret-free canonical template (`.claude/hooks-template.json`, git-tracked) plus a runnable verification command (`agent/verify_claude_hooks_config.py`, checked into Git, with its own test suite) now make this durable and independently re-checkable rather than "worked once, on one machine."

  - **Separate curated index, not a bigger version of the whole-repo one.** `agent/backend_rag_corpus.py` explicitly lists 10 documents (5 Customer-app source files, 2 test files, `docs/ACTION_QUEUE.json`, `docs/WORKBENCH_RELIABILITY_GAP_ANALYSIS.md`, `docs/LESSONS.md`) — never the whole repository. `agent/backend_rag_index.py` persists to its own `agent/.backend_rag_index/index.json`, a second local-JSON-file index alongside (not merging with) `agent/.rag_index/index.json`. Reused: the same embedding provider (`agent/embeddings.py`'s fastembed `bge-small-en-v1.5`, zero new model/key), the same "local JSON + numpy scan, no external vector DB" storage choice already made for the whole-repo index (still correct at ~80 curated chunks; introducing pgvector here — despite Postgres already existing for the event ledger — would be infrastructure added to say "vector database", not because retrieval needs it at this size).
  - **Chunking is boundary-aware, not blind fixed-window**, unlike the whole-repo index: Java files are split at class/member boundaries via brace-depth tracking (one chunk per method/constructor/field, one header chunk for package+imports+class decl — documented limitation: naive brace counting does not understand string/char literals containing `{`/`}`, acceptable for this small conventionally-formatted app, not a general Java parser), Markdown at heading boundaries, and `docs/ACTION_QUEUE.json` at its own `items` array (one chunk per catalogue entry). Any resulting chunk over 120 lines is sub-windowed (40 lines/8 overlap, same constants as the whole-repo index) so no single embedding call represents unbounded text.
  - **MCP stays ONE server, not two.** The curated retriever is exposed as a new `search_project_context` tool added to the EXISTING `agent/mcp_server.py` (alongside the pre-existing `semantic_repository_search`, which still serves the whole-repo index for the V3 CLI agent) rather than standing up a second MCP server process — both are already read-only by construction, and running two server processes for two read-only tools would be pure process-count overhead. `search_project_context`'s schema has no path/directory parameter at all (only `query`/`top_k`/`source_type`), so a natural-language query cannot be turned into an arbitrary filesystem read even in principle — verified in `agent/test_mcp_server.py`.
  - **Authorization boundary is structural, not a policy statement.** `agent/backend_planning.classify_backend_routing()` — the ONLY function that decides `DETERMINISTIC_ONLY`/`USE_RAG_MCP`/`REJECT_UNAUTHORIZED` — runs on the raw requirement text alone and is called BEFORE any retrieval; retrieved chunks (even an adversarial "ignore all security rules" fixture, see Eval 4) are never passed into it, into `risk_policy.classify`, or into `backend_catalogue.normalize_backend_requirement`/`apply_operation` — those three remain the sole authority for what is permitted, completely unchanged by this task. `agent/backend_planning.py`'s LLM impact-analysis step is advisory-only evidence (affected components, expected files, verification plan) with a deterministic `check_groundedness()` catching any claimed file that wasn't actually retrieved — the model's suggestions are never trusted, only checked.
  - **Routing keeps trivial deterministic operations off the RAG/LLM path on purpose**: `classify_backend_routing` checks `demo_catalogue.normalize_requirement` first (known static-HTML ops: heading/subtitle/footer/button text) and returns `DETERMINISTIC_ONLY` with zero retrieval/LLM cost; only requirements matching backend-context keywords (customer/service/controller/exception/validation/etc.) that also clear `risk_policy` route to `USE_RAG_MCP`. Verified via `agent/evals/routing_dataset.json` (14 hand-labeled cases, 100% routing accuracy including 100% on the zero-tolerance `REJECT_UNAUTHORIZED` subset at baseline).
  - **Evals are a distinct concern from unit tests**, per an explicit new Skill (`.claude/skills/ai-feature-evaluation/SKILL.md`): `agent/eval_runner.py` runs Eval 1 (retrieval Recall@3/Recall@5/MRR against `agent/evals/retrieval_dataset.json`, 12 hand-labeled cases) and Eval 2 (tool-routing accuracy against `agent/evals/routing_dataset.json`) with explicit initial thresholds (`recall_at_3>=0.40`, `mrr>=0.35`, `routing_accuracy>=0.85`, `security_case_accuracy==1.0` — zero-tolerance) chosen against this small dataset, not tuned to make the baseline look good after the fact. Baseline actually measured: recall@3=1.0, MRR=0.903, routing_accuracy=1.0 (see docs/PROJECT_STATE.json). ## Sprint 13 (2026-09-29): Standing Interview answers any on-book question -- mechanism, not exam answers

- **Which employer leads a generic answer is decided by the books' own attribution matrix, in code, before the model sees anything.** Each hands-on book ends in a table of `Technology / Personal classification: HANDS-ON | USED/EXPOSED | SYSTEM KNOWLEDGE | NOT USED`. `scripts/build_si_corpus.py` parses it into the corpus; `standing_interview.attribution_for()` maps the question's technology family to those rows and returns lead / used / not-used employers; retrieval for a generic question then fills its slots from the lead employers only, and the prompt is handed one line ("Your own record says: hands-on at BCBSA; not used at NRG Energy. Lead with BCBSA..."). Why not keep Sprint 11's per-employer balancing: balancing guaranteed coverage of every employer, which is exactly the "tour every employer" shape the Owner rejected for generic questions. Why not hard-code per-question answers: the six exam questions are a regression pack; the matrix has 66 rows and answers questions nobody wrote down. Balancing remains the fallback when the matrix has no row for a topic, so nothing that worked before refuses now.
- **A standing career map is placed in front of the model on every generate, and a corpus without one is not a corpus.** The map is a first-person brief derived only from the FINAL_V1 books, kept in the private repository (`books/SI_CAREER_MAP.md`, Owner decision 2026-09-29) and embedded by the corpus builder as `career_map` (format_version 2). `load_corpus()` returns None for a v1 file or an empty map, so a stale container cannot answer without it. Why: which six chunks score highest is not a reliable source of orientation (who, where, when); the map makes that constant.
- **Query rewrite before retrieval uses book vocabulary only.** "multithreading" never appears in the books; "CompletableFuture", "parallel", "fan-out" do. Fifteen families, every expansion term read out of the derived books, no employer names (that is the matrix's job). Measured effect: the multithreading question went from a refusal to best_score 0.6861 with the same threshold.
- **An extension-only leak hit earns ONE corrective retry; every other leak pattern still refuses immediately.** Gate run 2 refused a good answer about the approval boundary because the model named `write_tools.py` -- a public repository file, not a book identifier. The scan is not weakened: the retry's text goes through the whole scan and the voice gate, and a retry that still leaks is refused with `leak_retried=True` recorded for the review queue. Book numbers, "according to", private paths and pantheon names are never retried. Flagged for the Owner's veto because the Owner's instruction was "do not weaken leak/voice gates"; the judgement here is that a retry which still guarantees nothing leaked reaches the interviewer is an availability fix, not a weakening.
- **Private topics are refused deterministically before any model call.** The grounding threshold cannot do it (career words score well against career text -- the salary question scored 0.5725) and the decline gate only sees what the model chose to say; the model DEFLECTED politely instead of declining. Narrow on purpose: compensation, contact details, identity documents, age, family. Work authorisation and location are deliberately not gated -- the Owner has left that decision open.

## Sprint 13 (2026-09-29): one durable, stateful software-change workflow on LangGraph (BL-093/094/095)

- **LangGraph is a real dependency, chosen over a hand-rolled graph** (Owner decision 2026-09-29). `langgraph>=1.2,<2` in agent/requirements.txt, pinned by major; resolved against the installed 1.2.12 (`interrupt()`, `Command(resume=)`, `BaseCheckpointSaver.put/put_writes/get_tuple/list`, `JsonPlusSerializer`) before a line was written -- never from memory. Why not hand-rolled: the HITL primitive (`interrupt` / `Command(resume=)`) is exactly the suspend-and-resume this task needs, and the framework is a named technology in the Owner's target roles. Why it does not change the platform's deterministic-first stance: the graph decides ORDER; every authority decision (risk policy, the deterministic proposal from `demo_catalogue`, the write boundary's prefixes/extensions and hash binding, the allowed build goals, the human decision arriving only via `resume_workflow()` from an HTTP handler the model has no tool for) is the existing code, reused unchanged.
- **A NEW PARALLEL path; the Workbench run path is untouched** (Owner decision). `agent/web_server.py`'s synchronous in-process approval prompt, SSE stream and single-run slot are exactly as they were. Why: the Workbench is a live production surface; the durable path needed a different execution model (suspend, persist, resume across a process death), and rewriting a live surface's execution model on the same night as the Standing Interview P0 was the wrong risk. Cost accepted: two code paths that both apply a catalogue change; recorded, not hidden.
- **Checkpoints live in the ledger's Postgres, in two new tables applied by `event_ledger.ensure_schema()`** (Owner decision): `workflow_checkpoints` (one row per LangGraph checkpoint, whole checkpoint typed-serialised) and `workflow_checkpoint_writes` (pending writes, so an interrupt and its resume survive a restart). A direct port of `MemorySaver`'s semantics read out of langgraph-checkpoint 4.2.0, with one deliberate simplification -- the whole checkpoint per row instead of per-channel blob de-duplication -- because a checkpoint here is a few kilobytes and one readable row per step is what an operator debugging a stuck workflow wants. Fail-closed: a row that does not decode to a dict with `channel_values` raises (msgpack decodes a NUL-led garbage blob to the integer 0 without complaint -- found by the live store test, not by reasoning), and `describe_workflow()` reports CORRUPT rather than resuming.
- **This path SUPERSEDES the recovery philosophy in docs/DURABLE_EXECUTION_RECOVERY.md for the durable workflow only.** That document records "recovery is 'retry the whole operation fresh', not 'resume a partial one'" for the isolated-workspace Workbench/Triage paths -- still true for them. The durable workflow deliberately does the opposite: it resumes from the last checkpoint, and its single side-effecting stage (apply: write + commit in an isolated git workspace, binding hash in the commit subject) is idempotent by construction -- on any re-entry it first looks for its own commit and skips; if the checkpoint says the write happened but the workspace is gone, it FAILS SAFELY with that reason rather than write again. The crash drill (agent/workflow_drill.py) is the first real kill-signal test in this repository, closing the "honest gap" that document named. Crash drill run 7 (2026-09-29 00:01Z, all four scenarios in one foreground run): 22 of 22 assertions held -- a real child process killed after the git commit and before the apply checkpoint, resumed by a fresh process that recognised its own commit, did not write again, and ran compile/test/verify to COMPLETED with exactly one workflow commit; a kill after the apply checkpoint and before compile, resumed without the apply node running again; interrupted-before-approval still waiting in a fresh process; rejected-then-approved refused with no workspace ever created; a corrupted checkpoint row reported CORRUPT and refused to continue; a completed workflow refused a second approval. Earlier runs found and fixed three real defects on the way (workspace path not derivable after a mid-node kill; LangGraph's default async durability losing the apply checkpoint on a boundary kill -- now durability=sync; the store returning a decoded non-checkpoint instead of raising) and one latent one outside the workflow (ACT-022).
- **Operator-facing state is derived from the latest checkpoint, never from a second table.** workflow id, current state, completed states, pending human action, the deterministic decision, timestamps, outcome and the full transition list come from `describe_workflow()` reading the checkpoint's channel values; every transition is also a `workflow_transition` event and every human decision a `workflow_human_decision` event in the existing ledger. No parallel observability system.
- **Not built, on purpose:** a UI panel (the endpoints are driven by the Workbench operator or curl; a page was outside the bounded scope), pushing the workflow branch to origin (recorded as NOT_CONFIGURED when the token is absent, never assumed), Provider #2, multi-agent, vector DB.

## Governance (2026-10-02): mission-value and continuation controls, because execution controls alone did not stop anything

- **The diagnosis.** This project had unusually strong controls over **how** work is executed — evidence precedence, SKIPPED-is-not-PASSED, mutation gates, a sizing rubric with a computed tolerance band, independent evaluation triggers, a paid-call authorization gate — and almost no controls over **whether a given piece of work deserved the calendar time at all.** Deep Consensus ran six sprints to a pre-registered decision rule and the engineering was genuinely good throughout; what was missing was a boundary at which "does another sprint beat the next-best use of this time?" had to be answered and recorded.
- **The decision.** Add two boundaries and four terminal states, in CLAUDE.md's "Mission value gate": an **admission** boundary (an eleven-field Mission Card before substantial work starts) and a **continuation** boundary (five questions at every sprint/continuation boundary, ending in exactly one of `CONTINUE` / `REDIRECT` / `STOPPED_BY_RULE` / `NEEDS_OWNER_GOAL_REVIEW`). docs/CONSTITUTION.md §19 attaches §1/§5/§7/§10 to those boundaries so they can actually fire.
- **The nuance that matters, stated so the lesson is not overdrawn: it is NOT true that all six Deep Consensus sprints were known waste.** Sprint 6 was the authorized decisive experiment — pre-registered, run exactly once, and it answered its question. A programme that reaches a clean negative result has done its job. The defect was not that the experiment ran; it was that nothing between sprints had to justify the *next* one against the alternative use of the same days.
- **What the lesson actually is, in four lines.** (1) Implementation quality does not itself justify continuation — and good execution is the hardest case, because it feels like progress. (2) Earlier approval of a programme is not permanent authorization for its next increment. (3) Pre-registered pause/stop authority outranks momentum. (4) Sunk cost never authorizes another sprint.
- **A principle unattached to a decision boundary can be correct and operationally inert.** §1 (clear purpose), §5 (discernment), §7 (non-waste) and §10 (non-attachment) were all already written, already believed and already being followed as values — and none of them stopped anything, because none of them was evaluated at a point where stopping was the output. This is the single most reusable finding of the governance pass and it generalises well beyond this project: a value with no boundary to fire at is a value, not a control.
- **Also recorded: role architecture is separated from provider assignment.** docs/AI_COLLABORATION.md now states stable roles (final authority / strategic reasoning and challenge / implementation and repository operator / independent review / deterministic technical truth authority); which model currently holds which role is private current state, not public architecture. The prior version is preserved in that file marked SUPERSEDED 2026-10-02 — it had hard-coded a 2026 provider into the governance model, so a change in provider availability would have read as a change in governance.
- **Governance may interpret evidence; it may never rewrite it** (§19). Where a mechanical result and a human adjudication of the same frozen evidence differ, both are preserved and labelled. Erasing the disagreement would destroy the only proof that a process was followed rather than steered.
- **No new Deep Consensus architecture is authorized by any of this.** The hard guard is in CLAUDE.md; the closing record is docs/DEEP_CONSENSUS_FINAL_CLOSURE_2026-10-02.md.
