# AI Usage, Cost & Value Intelligence

Page: `/ai-usage` (public nav: "AI Usage"). Code: `agent/usage_intel/`.
Price and token-meaning sources: `docs/AI_USAGE_SOURCES.md`.
Built 2026-11-28. The whole implementation was generated by Claude (an AI
model) working in Claude Code. The owner set the requirements and approved
the scope decisions listed at the end.

## 1. What it answers, in plain words

A team using AI wants to know four things:

1. **What did AI cost?** Split by team, person, project, model, feature,
   workflow and session.
2. **What did it achieve?** Count tasks that were *verified* by a test, an
   assessment or a human, not tasks an AI says it finished.
3. **What is the cost of each verified result?** This includes the money
   spent on failed attempts and retries.
4. **Where can it improve?** Deterministic rules point at waste, with the
   evidence and a confidence level. Nothing is changed automatically.

The goal is more verified value per dollar, not the fewest tokens.

## 2. The three rules behind every number

| Rule | What it means on screen |
|---|---|
| **Unknown is not zero** | Missing data shows "unknown" plus a coverage count ("1004 of 1004 calls priced"). A total never silently treats a missing value as 0. |
| **Every number says where it came from** | Each figure carries a provenance label: `provider_reported`, `app_measured`, `estimated`, `estimated_partial`, `estimated_back_applied`, `imported`, `manual`, `demo` or `unavailable`. |
| **Money is labelled by how it is paid** | `metered_api` is pay-per-token spend, shown as a list-price estimate. `equivalent_api_value` is subscription usage valued at API prices and is **not money spent**. The two are never added together as "spend", and budgets count metered spend only. |

Module by module (`agent/usage_intel/`):

| File | Job |
|---|---|
| `events.py` | The `UsageEvent` record and its enums: `Source` (provenance), `BillingCategory`, `RequestType`. Converters for Anthropic and OpenAI usage objects. Deterministic event IDs (`make_event_id`), so a retried write cannot double count. |
| `pricing.py` | `estimate(event)`: tokens × the published price **in force on the event's date**. It applies the 1-hour cache-write rate and Haiku's long-context tier. An event dated before the first verified price is labelled `estimated_back_applied`. Missing input or output gives `estimated_partial`. An unknown model gives no price, never 0. |
| `analytics.py` | Filters (date range, team, person, project, model, activity…), de-duplication, leaf-only counting (an agent run groups its model calls and carries no tokens itself, so nothing is counted twice), totals with coverage, breakdowns, daily series, session list and session drill-down. |
| `outcomes.py` | `Outcome` (one task's result and how it is known) and `value_metrics`: success, first-attempt and rework rates, cost per verified success, cost of failed attempts, and measured versus estimated time saved, kept apart. |
| `learning.py` | `LearningRecord` and learning metrics. A concept counts as verified only after an assessment or a reviewed exercise, never because an explanation was generated. It also imports records from JSON or CSV. |
| `recommend.py` | Six deterministic rules. Each finding states evidence, why it matters, the suggested action, an estimated benefit (labelled as an estimate), confidence, limitations and whether evaluation is required before acting. |
| `compare.py` | Model comparison per activity. It suggests a model only when two or more models have at least 10 tasks each with verified outcomes, and the suggestion is advisory only. |
| `access.py` | Roles (`demo_viewer`, `member`, `team_lead`, `org_admin`, `owner`), the scope each role sees, and a filter check that raises `Forbidden`. |
| `store.py` | Live data: maps existing ledger rows to usage events (re-estimating cost so every row uses one method) and reads and writes outcomes, learning records and the audit log. |
| `demo.py` | The fictional dataset (fixed seed, dates relative to today). |
| `api.py` | Pure request handlers: dataset choice, role checks, validation and response envelopes with legends. |

## 4. One request, end to end

1. The gateway calls a model. The provider returns a usage object, and the
   existing sink writes a `model_usage` row to `delivery_events`.
2. The owner opens `/ai-usage`, chooses "Live" and enters the owner token. The
   token is kept in this browser tab only and sent as the `X-Owner-Token` header.
3. `web_server.ai_usage_view` checks the token (`owner_auth`) and gets an
   `owner` principal. Without the token the visitor is a `demo_viewer`, and
   `dataset=live` returns **403**, never a silent fallback to demo data.
4. `api.load` → `store.load_events` → `row_to_event` labels the row
   `metered_api` with `provider_reported` tokens, or, for Claude Code,
   `equivalent_api_value` with `imported` tokens. `pricing.estimate` then
   computes the cost.
5. `analytics` and `outcomes` compute totals, coverage and value. The page
   renders them with `textContent`, so no data is ever parsed as HTML.

The test that proves this path end to end against a real Postgres is
`agent/test_usage_intel_store.py` (`LiveStoreTests`). It inserts a ledger
row, loads it through the API and checks the hand-computed cost of $0.65. It
runs in CI's `ledger-postgres` job.

## 5. Database tables (appended to `infra/event-ledger/schema.sql`)

| Table | Holds | Notes |
|---|---|---|
| `delivery_events` (existing) | model usage rows | No new columns. Prompt and response excerpts there are ignored by this feature. |
| `usage_outcomes` | one row per recorded task outcome | evidence, status, attempts, review minutes, time saved and its source |
| `learning_records` | learning events | source is server-assigned: `manual` or `imported` |
| `usage_audit_log` | who wrote what, when | every owner write is logged |

## 6. HTTP endpoints

| Method + path | Who | Returns |
|---|---|---|
| `GET /ai-usage` | anyone | the page |
| `GET /api/ai-usage/{overview,breakdown,sessions,recommendations,models,learning}` | anyone for `dataset=demo`; owner for `dataset=live` | JSON with `dataset`, `demo_label`, `window` and both legends |
| `GET /api/ai-usage/sessions/{id}` | as above | the session drill-down |
| `GET /api/ai-usage/meta` | anyone | enums and legends |
| `POST /api/ai-usage/outcomes` | owner only | records an outcome; unknown fields are rejected |
| `POST /api/ai-usage/learning-records` | owner only | manual records or a JSON/CSV import; the client may not set `source` or `user_id` |

Query parameters: `range` (`today`, `yesterday`, `7d`, `30d`, `month`,
`custom` with `start`/`end`), plus the filters `team_id`, `user_id`,
`project_id`, `provider`, `model`, `feature`, `activity_category`,
`workflow_id` and `billing_category`. Breakdowns take `by`.

## 7. How the money is calculated

```
cost = uncached_input × input_rate
     + cache_read     × cache_read_rate
     + cache_write_5m × cache_write_rate + cache_write_1h × cache_write_1h_rate
     + output (incl. reasoning) × output_rate            (all per 1M tokens)
```

* **Token meaning differs by provider.** Anthropic's `input_tokens` excludes
  cached tokens. OpenAI's includes them, so `from_openai` subtracts cached
  reads and writes first. Reasoning tokens are billed as output.
* The price used is the one in force on the event's date, from
  `pricing_config._PRICING_HISTORY`. Each entry has its source URL and access
  date.
* **Cost per verified success** = all list-price cost of the tasks, including
  failed attempts ÷ the number of verified successes. It is an honest number,
  so failures make it go up.
* **ROI** appears only when an hourly rate is supplied, and is labelled ESTIMATE.

Hand-checked fixtures in `agent/test_usage_intel_core.py`: an Opus call costs
$0.108, a Haiku long-context call $0.026, and the fixture set totals $0.95.
The billing split is checked with $0.30 + $0.20 metered = $0.50 spend, and
$1.50 subscription value.

## 8. Security and privacy

* **Public visitors see fictional demo data only.** It is built in memory and
  never stored, every row is marked `demo`, and a banner says so.
* Live data, writes and learning records need the owner token. A wrong or
  missing token returns 403 (tested in `test_ai_usage_page.py` and
  `e2e/ai-usage.spec.js`).
* No prompt, response or source text is stored or shown for analytics, only
  metadata.
* The token is never placed in a URL or in localStorage. A static test
  enforces this.
* Every write is validated against an allow-list of fields, and every write is
  audit-logged.
* **No logins.** The owner chose role checks without logins. A real
  multi-user deployment would need an identity provider before the
  `member`/`team_lead`/`org_admin` roles could mean anything. The role model
  and scope filters exist and are tested, but only `demo_viewer` and `owner`
  are reachable today.

## 9. Known limitations, stated plainly

* **Provider billing is not connected** (owner decision: no live billing
  APIs). The "Provider-reported cost" tile therefore shows unknown. Every cost
  is a list-price estimate, not an invoice. Discounts, batch pricing and
  credits are not reflected.
* **Live outcomes start empty.** Cost per verified success on live data needs
  outcomes recorded through `POST /api/ai-usage/outcomes` (owner) or by a
  future CI hook. Until then it shows unknown.
* The gateway's own usage sink still records a random event ID and
  `environment="local"`, and does not record duration or pricing version. The
  read side re-estimates cost, so totals are right, but enriching the sink is
  open work.
* Subscription plans (a flat fee) are not modelled as spend, because no plan
  price was supplied or verified. Subscription usage is shown only as
  equivalent API value.
* Demo budgets are display-only. The live gateway's real budgets (daily,
  per-run and per-request caps in Postgres, failing closed) are separate and
  shown on `/usage`.
* Recommendations are rules over recorded data and need enough volume. On
  small live data most of them stay silent, which is the intended behaviour.
* Same-model review: the tests and the review were written by the same AI
  family that wrote the code. Independent human review is the remaining check.
